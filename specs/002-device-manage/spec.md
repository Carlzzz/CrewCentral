# Feature Specification: Device 管理与监控

**Feature Branch**: `002-device-manage`  
**Created**: 2026-04-07  
**Status**: Draft  
**Input**: 功能：Device 管理与监控 (short name: device-manage)；自动注册、心跳、管理端管控与黑名单、真实 IP、Redis+PostgreSQL 心跳路径、管理 UI、依赖 auth-login；非目标见 Assumptions。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 设备静默注册与心跳保活 (Priority: P1)

客户端在通过平台身份校验后，按约定静默上报设备基础信息，完成首次注册或信息更新；并按固定频率发送心跳，使平台能区分在线与离线状态。

**Why this priority**: 没有可识别的设备与时间维度上的「在线」事实，后续监控、管控与合规审计无从谈起。

**Independent Test**: 仅用已鉴权客户端模拟「上报一次设备信息 + 周期性心跳」即可验证注册与在线时间戳更新，无需管理端 UI。

**Acceptance Scenarios**:

1. **Given** 客户端已完成身份鉴权且持有有效调用身份，**When** 静默上报设备基础信息，**Then** 平台以稳定设备标识完成创建或更新，并关联到当前用户身份。
2. **Given** 客户端按约定频率发送心跳，**When** 心跳被服务端接受，**Then** 该设备的「最近在线」时间被更新，且高频路径不拖垮核心持久化存储（见 Requirements 中的性能约束）。
3. **Given** 请求经过反向代理，**When** 服务端解析客户端地址，**Then** 设备记录中的客户端地址反映真实来源侧（按可信转发头规则），而非仅代理机地址。

---

### User Story 2 - 管理端设备浏览与管控指令 (Priority: P2)

管理员在 Web 后台查看已接入设备列表，按状态、所属用户、网络地址等维度筛选；可对单台设备执行「强制下线」或「加入黑名单」等管控动作。

**Why this priority**: 运营与安全团队需要可视化与处置能力，才能把注册/心跳数据转化为可控风险面。

**Independent Test**: 在已有若干设备数据的预置环境中，仅验证列表、筛选与指令下发及审计痕迹，可不依赖真实客户端心跳。

**Acceptance Scenarios**:

1. **Given** 管理员已登录且具有管理权限，**When** 打开设备列表页，**Then** 能看到设备关键字段（至少含标识、状态、关联用户、网络侧地址、最近在线时间等约定列），且在线/离线/封禁状态有清晰可辨的视觉区分。
2. **Given** 管理员使用搜索或过滤条件，**When** 提交筛选，**Then** 结果集与条件一致且在可接受时间内呈现。
3. **Given** 管理员对某设备发起「强制下线」或「加入黑名单」，**When** 指令成功受理，**Then** 系统记录操作者、目标与时间，且后续该设备在相关通道上被施加对应限制（与 Story 3 衔接）。

---

### User Story 3 - 黑名单与强制下线的请求拦截 (Priority: P2)

已被列入黑名单或已被强制下线的设备，在尝试继续登录相关流程或发送心跳时，服务端拒绝服务并返回明确、可机器识别的错误信息，供客户端与运维区分原因。

**Why this priority**: 若仅后台展示「封禁」而通道仍接受流量，则管控无效，风险窗口持续存在。

**Independent Test**: 将测试设备置于黑名单或下线状态后，单独用自动化请求验证登录与心跳接口的拒绝语义，无需完整管理 UI。

**Acceptance Scenarios**:

1. **Given** 设备处于黑名单状态，**When** 其发起需要身份延续或保活的请求，**Then** 请求被拒绝并返回与「正常业务错误」可区分的错误类别。
2. **Given** 设备被强制下线，**When** 其继续使用旧会话或令牌尝试保活，**Then** 服务端拒绝并返回可观测原因（与产品错误码策略一致）。
3. **Given** 设备从黑名单移除（若产品提供解封流程），**When** 满足解封条件后再次请求，**Then** 恢复与策略一致的正常处理路径。

---

### Edge Cases

- 心跳丢失或间隔抖动：平台在合理超时后应将设备视为离线，避免「永远在线」假阳性；超时阈值在规格或运营参数中可配置。
- 多网卡/虚拟网卡环境：MAC 与 IP 可能变化；以稳定设备标识为主键策略，网络信息作为辅助展示与检索维度。
- 转发头伪造：仅信任来自可配置受信代理段的 `X-Forwarded-For`（或等价链），并对链尾与链解析规则文档化，防止任意客户端伪造出口 IP。
- 同一用户多设备：列表与操作必须定位到单设备粒度，避免误伤同用户其他设备。
- 高频心跳洪峰：必须通过「热路径写缓存 + 异步批量落库」满足性能约束；降级策略（采样、限流）若启用须在规格中声明并评估对监控准确性的影响。

## Requirements *(mandatory)*

### Functional Requirements

**设备生命周期与通道**

- **FR-001**: System MUST 在客户端已通过平台身份校验的前提下，接受静默设备注册/更新请求；请求 MUST 携带稳定设备标识（与宪章「设备上报」幂等策略一致），并绑定当前用户身份上下文（由既有 auth-login 解析）。
- **FR-002**: System MUST 采集并持久化（直接或经异步路径）下列**业务所需**最小字段：出口侧客户端地址（经可信转发解析）、MAC 地址、操作系统版本、客户端版本；MUST NOT 采集与设备管控无关的额外软硬件隐私（如完整硬件指纹、无关传感器列表），除非经单独合规评估并文档化。
- **FR-003**: System MUST 支持按可配置间隔（默认量级为「数分钟」）接收心跳，并更新设备「最近在线」时间语义。
- **FR-004**: System MUST 在反向代理/负载均衡部署下，从受信转发头（如 `X-Forwarded-For`）解析真实客户端侧地址用于设备记录与检索；解析规则（受信跳数、链尾选择）MUST 可配置且默认安全。

**性能与持久化**

- **FR-005**: 对高频心跳更新，System MUST 先写入 **Redis（或等价的内存型缓存/流式缓冲）** 等低延迟层，再按批量、异步方式持久化到 **PostgreSQL**；MUST NOT 让每次心跳直接同步打满主业务库写入容量。

**管理与安全**

- **FR-006**: System MUST 提供 Web 管理端设备列表：顶部搜索/过滤（至少：在线状态、所属用户、IP 段或单地址），主体为表格展示；行内需有在线（绿）、离线（灰）、封禁（红）等可访问视觉标识；行末提供「踢下线」「封禁」入口（标签可按产品统一用语）。
- **FR-007**: System MUST 对所有管理写操作执行管理员鉴权（与宪章一致），并记录审计信息（谁、何时、对哪台设备、何种动作）。
- **FR-008**: System MUST 在设备处于黑名单时，拒绝其登录延续与心跳等关键路径，并返回稳定错误码/错误类别供客户端与集成方处理。
- **FR-009**: 「强制下线」MUST 使既有会话/令牌在策略上失效或不可用于保活，直至符合重新鉴权条件；具体与 auth-login 令牌模型的衔接在计划中细化，但行为对外可验证。

**集成依赖**

- **FR-010**: System MUST 依赖 auth-login 提供的请求鉴权与用户身份解析；设备相关 API MUST 仅对已通过身份校验的调用方开放（管理端与会话策略除外，按角色区分）。
- **FR-011**: 管控指令的实时生效路径 MAY 依赖客户端全局轮询或已存在的 WebSocket 等长连接；若当前工程尚未具备长连接，MUST 以保证「下一次心跳或下一次鉴权前生效」的最低保证在规格/发布说明中声明。

### Key Entities *(include if feature involves data)*

- **Device（设备）**: 稳定设备标识、关联用户、网络与管理字段（在线/离线/封禁）、最近在线时间、创建/更新时间；可选存储展示用 MAC、OS、客户端版本（最小集）。
- **DevicePresence / Heartbeat（在线事实）**: 与设备关联的心跳时间序列或最近快照；热路径落在缓存，异步合并入持久库。
- **AdminAction / Audit（管控审计）**: 管理员、目标设备、动作类型（下线/封禁/解封）、时间戳、可选备注。
- **Blocklist（黑名单）**: 设备或设备标识级别的封禁状态及原因码、生效时间。

## Constitution Check *(mandatory)*

*对照 `.specify/memory/constitution.md` 自证；与宪章 MUST 冲突时不得静默忽略，须在 Assumptions 或计划中写明例外与替代控制。*

- [x] **固定技术栈**：本规格不绑定具体语言；实现须符合宪章 Python/FastAPI 与 React 栈；Redis/PostgreSQL 为用户给定的性能与持久化约束。
- [x] **子路径部署**：管理端页面与 API MUST 服从统一 Base Path；与 auth-login 同站部署时的路由、Cookie、代理规则在计划中一并核对。
- [x] **双轨认证**：客户端 API 使用 Bearer JWT；管理 Web 使用会话或等价机制；边界在集成章节说明。
- [x] **契约优先**：设备注册/心跳/管理动作的路径、字段、错误码与 `rc` 约定 MUST 在后续合同与计划中落地。
- [x] **领域约束**：与宪章「设备上报」幂等及 JWT 用户绑定一致；不扩展技能包/下载等业务规则除非显式依赖。
- [x] **安全与运维**：HTTPS、管理写鉴权、敏感信息最小化、关键操作日志在本规格 FR 中已体现。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 在实验室条件下，单客户端按默认心跳间隔连续运行 1 小时，平台侧「在线」状态与最近在线时间戳与心跳节奏一致，无明显漂移（允许文档化的小幅聚合延迟）。
- **SC-002**: 在模拟不低于文档化目标并发心跳的场景下，核心持久化库的每秒同步写入次数不随心跳线性爆炸增长（即热路径满足 FR-005 的分流效果可验证）。
- **SC-003**: 管理员在典型数据量（例如不少于 500 条设备记录）下，常用筛选组合在 3 秒内完成列表首屏展示（以用户可感知为准）。
- **SC-004**: 对黑名单设备的拒绝请求，100% 返回可分类错误（与正常业务失败可区分），且在重复试验中结果一致。

## Assumptions

- auth-login 已提供可集成的用户身份与 JWT 校验链；本功能在其之上扩展设备领域模型。
- 生产环境前置 **Nginx（或等价）** 且可配置受信代理网段；开发环境可用简化规则并醒目标注风险。
- Redis 与 PostgreSQL 为环境已提供或可同期交付；具体拓扑（单实例/集群）由运维决定，不影响本规格对外行为。
- 客户端已具备全局轮询或长连接之一用于接收管控结果；若仅有轮询，「实时性」以产品可接受的延迟表述为准。

**非目标（明确排除）**：设备的远程桌面或命令行级接管；客户端崩溃日志自动分析与 APM 级运维监控（可归入独立运维系统）。
