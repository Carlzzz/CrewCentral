# Feature Specification: Docs 帮助文档系统（docs-page）

**Feature Branch**: `005-docs-page`  
**Created**: 2026-04-07  
**Status**: Draft  
**Input**: User description: 功能：Docs 帮助文档系统 (short name: docs-page)；范围含结构化层级、Markdown 渲染、全文搜索、slug 约束、前后台布局；非目标含 WYSIWYG 与用户评论。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 读者按 slug 阅读文档与导航 (Priority: P1)

作为产品用户或集成方，我希望通过稳定、可分享的 URL（基于语义化路径）打开帮助文档，并在页面内看到清晰的目录、正文与大纲，以便快速找到操作步骤或 API 说明。

**Why this priority**: 没有可访问、可分享的阅读体验，文档系统无法对外产生价值。

**Independent Test**: 仅发布若干篇带层级的文档后，访客无需登录即可通过给定 slug 打开页面、在侧栏切换章节并阅读渲染后的正文（含代码块与表格等常见排版）。

**Acceptance Scenarios**:

1. **Given** 已存在一篇可访问的文档节点且 slug 为约定路径，**When** 访客打开该 slug 对应的公开地址，**Then** 页面展示标题、渲染后的正文及可用的页面内大纲（TOC）。  
2. **Given** 文档树存在多级父子关系，**When** 访客在阅读页查看目录，**Then** 目录反映父子层级且当前文档在树中被标识（高亮或展开）。  
3. **Given** 正文中包含代码块、表格与图片引用，**When** 页面渲染完成，**Then** 代码具备可读样式、表格与图片按预期展示（图片地址合法时）。  

---

### User Story 2 - 管理员维护目录与 Markdown 内容 (Priority: P2)

作为文档管理员，我需要在后台用树状结构管理文档层级（含拖拽调整），并在右侧使用 Markdown 双屏编辑（一侧编辑、一侧预览），以便统一维护规范、避免富文本混乱。

**Why this priority**: 内容可持续运营依赖后台；可与阅读体验分阶段交付，但需尽早形成「发布—前台可见」闭环。

**Independent Test**: 管理员登录后能够新建/编辑/调整层级/发布内容，保存后前台读者可见更新且 slug 冲突时被拒绝并提示。

**Acceptance Scenarios**:

1. **Given** 管理员已登录管理后台，**When** 在树中创建子节点并保存合法 Markdown 与唯一 slug，**Then** 前台可通过该 slug 访问新内容。  
2. **Given** 管理员拖拽调整某节点的父级或顺序，**When** 保存成功，**Then** 前台目录树顺序与层级与后台一致。  
3. **Given** 管理员尝试保存与现有节点冲突的 slug，**When** 提交保存，**Then** 系统拒绝并提示原因。  

---

### User Story 3 - 全文搜索 (Priority: P3)

作为读者，我希望在顶部搜索框输入关键词后，得到与标题和正文相关的文档列表，以便在文档量大时仍能定位内容。

**Why this priority**: 仅靠目录浏览在规模大时效率低；在基础阅读与管理闭环可用后，搜索能显著提升检索效率。

**Independent Test**: 在有多篇文档的数据下，搜索唯一关键词仅返回包含该词的文档；无结果时给出明确空状态。

**Acceptance Scenarios**:

1. **Given** 多篇文档的正文或标题包含某关键词，**When** 用户提交搜索，**Then** 结果列表仅包含匹配的文档条目且可跳转到对应 slug。  
2. **Given** 无任何文档匹配，**When** 用户提交搜索，**Then** 系统展示无结果说明且不报错。  

---

### Edge Cases

- slug 重复或非法字符、与系统保留路径冲突时的处理与提示。  
- 父节点被删除或移动时，子节点的归属与链接有效性。  
- 单篇文档体积很大时的加载与编辑体验（是否分段或懒加载由实施阶段在保证可读性的前提下处理）。  
- 图片外链失效或路径错误时的降级展示。  
- 两名管理员同时编辑同一文档时的冲突或后写覆盖策略（至少不静默丢稿）。  
- 搜索特殊字符或空查询时的行为（明确提示或忽略无效输入）。  

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 支持按父子层级组织文档节点，并区分文档类型或用途（例如操作指南、API 接入说明、FAQ 等），以便形成可浏览的树形信息架构。  
- **FR-002**: 每个对外可访问的文档节点 MUST 具有全局唯一的语义化 **slug**，用于 URL 路径与分享；对外链接 MUST 以 slug 为主而非仅依赖内部自增标识。  
- **FR-003**: 系统 MUST 将文档正文以 Markdown 纯文本形式存储，并在前台渲染为 Web 可读页面，支持常用语法（包括但不限于标题、列表、链接、代码块、表格、图片）。  
- **FR-004**: 系统 MUST 在阅读页提供页面内大纲（TOC），与正文标题结构对应，便于长文跳转。  
- **FR-005**: 系统 MUST 提供阅读页布局：含顶部导航与全局搜索入口、侧栏目录树、主体渲染区与大纲区域；在窄屏下允许以抽屉或折叠方式呈现侧栏，保证可访问性。  
- **FR-006**: 系统 MUST 提供全文搜索能力，检索范围至少包含文档标题与正文，并返回可导航至目标文档的结果列表。  
- **FR-007**: 系统 MUST 提供管理后台：左侧树状目录管理（支持拖拽调整层级与顺序）、右侧 Markdown 双屏编辑（编辑与预览分区展示）。  
- **FR-008**: 系统 MUST 对管理端写操作执行身份鉴别与权限控制（仅授权管理员可维护文档）；公开阅读与搜索的可见范围在规格或策略中明确（默认：已发布内容对匿名读者可见，草稿仅管理员可见）。  
- **FR-009**: 系统 MUST 与既有 Web 应用的路由与部署基路径策略兼容，避免破坏统一入口与登录态策略。  
- **FR-010**: 系统 MUST 明确非目标边界：**不提供** 所见即所得富文本编辑器；**不提供** 面向终端用户的文档评论或社区发帖功能。  

### Key Entities *(include if feature involves data)*

- **文档节点（Doc Node）**：表示树中一项；含 slug、标题、正文（Markdown）、在树中的位置（父节点、同级排序）、类型/分类（如指南/API/FAQ）、发布状态（草稿/已发布等）、版本或更新时间。  
- **文档树视图（Doc Tree View）**：面向阅读侧与管理侧的层级展示与当前选中项；由节点父子与排序推导，非必须单独持久化。  
- **搜索结果项（Search Hit）**：包含匹配文档的标识（slug、标题）、摘要或高亮片段、跳转所需信息。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 90% 的「打开指定 slug、读完单篇操作指南」任务可在 **3 分钟内**由用户独立完成（含导航与滚动）。  
- **SC-002**: 在不少于 **50 篇**样例文档下，针对已知关键词的搜索，用户能在 **10 秒内**从提交搜索到打开目标文档（不含网络异常）。  
- **SC-003**: 管理员完成「新建一篇、挂载到树、发布」的闭环，**80%** 情况下在 **10 分钟内**完成且无 slug 冲突类错误。  
- **SC-004**: 上线后首月，因「找不到文档或链接失效」产生的支持类反馈相对上线前基线 **下降 30%**（或通过抽样问卷「是否容易找到说明」满意度 ≥ 80%）。  

## Assumptions

- 首期以 **Web** 阅读与管理为主；打印/PDF 导出非必须，除非后续迭代纳入。  
- 文档媒体资源（图片等）可采用外链或项目约定的静态资源路径；对象存储细节由部署与计划说明。  
- 全文搜索的底层实现（例如关系型库内置全文检索或专用搜索组件）由实施阶段选型，以满足 FR-006 与性能目标为准。  
- 管理员身份与现有管理端认证体系统一；无需单独面向读者的账号体系即可满足本规格。  
- SEO 友好性通过语义化 slug、合理标题与可抓取公开页达成；站点地图等进阶 SEO 非首期强制范围。
