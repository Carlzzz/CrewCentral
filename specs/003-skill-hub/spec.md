# Feature Specification: Skill 技能下发中心（Skill Hub）

**Feature Branch**: `003-skill-hub`  
**Created**: 2026-04-07  
**Status**: Draft  
**Input**: User description: "/speckit.specify 功能：Skill 技能下发中心 (short name: skill-hub)"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 技能库管理与版本治理 (Priority: P1)

作为运营/管理员，我可以在后台上传技能包、查看技能元数据与版本历史，并维护同一技能的多个版本，从而持续发布与回滚技能而不影响其他技能。

**Why this priority**: 这是整个能力的入口，没有可管理的技能库就不存在后续分发、权限绑定与热更新价值。

**Independent Test**: 管理员完成一次技能包上传并在详情页看到该技能的新版本与更新日志，同时历史版本仍可查看且不被覆盖。

**Acceptance Scenarios**:

1. **Given** 管理员已登录后台，**When** 上传一个包含技能元信息的技能包，**Then** 系统保存该版本并展示版本号、描述、适用平台等信息。  
2. **Given** 某技能已有多个版本，**When** 管理员进入技能详情，**Then** 可以看到版本历史与每次更新日志。  
3. **Given** 上传包缺少必要元信息或内容损坏，**When** 提交上传，**Then** 系统拒绝并返回明确原因，不创建新版本记录。

---

### User Story 2 - 用户/设备维度的技能授权与参数下发 (Priority: P1)

作为管理员，我可以为用户或用户组配置可用技能，并为每个技能填写自定义 JSON 参数，使不同用户/设备收到差异化能力与配置。

**Why this priority**: 分发控制是业务核心，直接决定谁能用什么技能以及技能运行参数是否正确。

**Independent Test**: 在后台对指定用户绑定技能并保存参数后，目标用户设备请求技能清单时返回对应技能与参数，非目标用户不返回该技能。

**Acceptance Scenarios**:

1. **Given** 管理员在权限配置页选择用户（或用户组），**When** 勾选技能并保存参数，**Then** 系统建立绑定关系并保存参数。  
2. **Given** 同一技能绑定给多个对象，**When** 分别设置不同参数，**Then** 系统能按对象返回对应参数，不互相覆盖。  
3. **Given** 绑定策略包含设备平台限制（如仅 Windows），**When** 非目标平台设备请求清单，**Then** 该技能不出现在返回结果中。

---

### User Story 3 - 客户端动态拉取与静默热更新 (Priority: P2)

作为客户端，我可以拉取当前可用技能清单与最新版本号；当发现新版本时自动下载并替换本地技能包，并在加载前完成完整性校验。

**Why this priority**: 这是最终交付价值的消费链路，依赖前两项能力但可独立验证升级体验与安全性。

**Independent Test**: 客户端在旧版本状态下拉取清单后检测到新版本，成功下载并通过完整性校验后完成替换；若校验失败则拒绝加载并保持旧版本。

**Acceptance Scenarios**:

1. **Given** 客户端携带有效身份请求技能清单，**When** 服务端计算授权结果，**Then** 返回该客户端可用技能、最新版本与下载凭据。  
2. **Given** 客户端本地版本低于服务端版本，**When** 触发更新流程，**Then** 客户端静默下载并替换为新版本。  
3. **Given** 下载文件与服务端下发哈希不一致，**When** 客户端校验，**Then** 客户端拒绝加载该文件并上报失败状态。

---

### Edge Cases

- 同一技能短时间内连续上传多个版本时，系统如何保证版本顺序与可追溯性。  
- 用户同时命中“用户级授权”和“用户组授权”且参数冲突时，系统如何按固定优先级合并。  
- 设备离线后恢复连接，服务端如何保证其拿到当前最新且仍有权限的技能集合。  
- 下载凭据过期或被复用时，系统如何拒绝请求并指导客户端重试获取新凭据。  
- 权限在客户端更新过程中被撤销时，系统如何阻止后续下载并避免继续分发。  
- JSON 参数格式合法但业务字段缺失时，系统如何提供可理解的校验反馈。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 提供后台技能库管理能力，支持上传技能包并提取至少版本、描述、适用平台等元数据。  
- **FR-002**: 系统 MUST 支持同一技能的多版本共存，并可在技能详情中查看完整版本历史与更新日志。  
- **FR-003**: 系统 MUST 在上传校验失败时阻止发布，并向管理员返回可操作的失败原因。  
- **FR-004**: 系统 MUST 提供技能分配能力，可将技能绑定到特定用户或用户组。  
- **FR-005**: 系统 MUST 支持对每个绑定关系维护可扩展、可查询的结构化 JSON 配置参数，并在下发时返回对应参数。  
- **FR-006**: 系统 MUST 在客户端请求技能清单时，根据身份、绑定关系和设备条件（含平台）返回“可用技能 + 最新版本 + 下载信息”。  
- **FR-007**: 系统 MUST 支持短时效下载凭据或等效防盗链机制，避免长期可复用的公开下载地址。  
- **FR-008**: 系统 MUST 在下发中包含技能包完整性校验信息（哈希值），并要求客户端在本地加载前完成校验。  
- **FR-009**: 系统 MUST 支持客户端静默热更新触发：当服务端版本高于本地版本时可发起下载替换。  
- **FR-010**: 系统 MUST 在授权变更后使后续技能清单请求立即反映新策略（新增、撤销、参数变更）。  
- **FR-011**: 系统 MUST 提供后台权限配置界面，支持“选对象（用户/设备）+ 选技能 + 编辑 JSON 参数”的连续操作流。  
- **FR-012**: 系统 MUST 提供后台技能大厅视图，支持全局技能列表/卡片展示与进入详情页查看版本历史。  
- **FR-013**: 系统 MUST 与现有登录认证体系复用身份上下文，确保后台操作可追溯到管理员主体。  
- **FR-014**: 系统 MUST 对关键操作（上传、绑定变更、下载授权发放）保留可审计记录。  
- **FR-015**: 系统 MUST 明确本模块边界：不负责客户端技能运行时解释执行，也不提供在线 IDE 能力。

### Key Entities *(include if feature involves data)*

- **技能（Skill）**: 表示一个可被分发的能力单元，包含唯一标识、名称、描述、适用平台、当前状态等。  
- **技能版本（Skill Version）**: 表示技能的可发布版本，包含版本号、发布说明、完整性哈希、下载访问信息、发布时间等。  
- **授权绑定（Assignment）**: 表示技能与用户/用户组/设备条件之间的关系，包含生效状态、优先级和可扩展 JSON 参数。  
- **分发清单（Distribution Manifest）**: 面向客户端返回的聚合结果，包含该客户端当前可见技能、目标版本、配置参数与下载凭据。  
- **下载凭据（Download Token）**: 短时效访问授权，绑定技能版本与访问主体，用于控制下载链接可用性与有效期。  
- **操作审计记录（Audit Record）**: 记录上传、分配、撤销、配置修改等管理行为的主体、时间与变化内容。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 95% 的技能上传操作可在 2 分钟内完成“上传-解析-可见于技能详情”闭环。  
- **SC-002**: 对已正确授权的目标客户端，99% 的技能清单请求可在 3 秒内返回可用技能与目标版本信息。  
- **SC-003**: 90% 的客户端版本升级在首次检测到新版本后 10 分钟内完成静默更新并通过完整性校验。  
- **SC-004**: 对未授权主体或过期下载凭据，100% 的下载请求被拒绝且不会泄露可长期复用的下载地址。  
- **SC-005**: 上线后 30 天内，与“技能权限误配/参数错配”相关的人工回滚或紧急修复工单占比低于 5%。  
- **SC-006**: 管理员在权限配置页完成“选对象-选技能-填参数-保存”的首次成功率达到 90% 以上。

## Assumptions

- 复用现有 `auth-login` 身份体系，管理员身份来源与现有后台一致。  
- 技能分发策略允许与 `device-manage` 的设备属性（例如平台）联合判断。  
- 客户端具备基础下载与本地文件替换能力，本模块只定义分发与校验契约。  
- 自定义参数采用结构化 JSON 文档存储，满足灵活扩展和条件查询能力（实现阶段遵循项目数据策略）。  
- 下载凭据默认采用短时效机制（例如分钟级），具体时长由后续计划根据安全与可用性权衡确定。  
- 非目标范围（客户端运行时引擎、在线 IDE）不纳入本期交付。
