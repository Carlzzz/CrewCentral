## 1. 产品概述
### 1.1 产品定义
**woicrew中央控管系统** 是企业 AI Agent 体系中的中心化管理平台，承担以下四类核心职责：

1. **应用管理**：统一维护客户端版本、下载地址与发布说明；
2. **认证中心**：对接企业 IAM，为 Web 管理端和客户端提供身份认证能力；
3. **技能仓库**：统一管理技能包的上传、审核、展示、下载；
4. **设备管理**：统一记录设备、用户与客户端间的关系，为后续授权、审计、运营提供基础台账。

从对外形态看，它同时表现为三种组合：营销/门户首页、工具型 Web 应用、管理后台，以及一组给客户端使用的无 UI API。前端为 React + Vite SPA，通过子路径挂载；后台含独立管理布局；客户端通过开放 API 接入。

### 1.2 产品定位
本产品是企业 AI Agent 平台中的 **控制面与分发面**，不是客户端运行时，也不是模型代理网关。它负责“管控、配置、分发、记录”，而不是“本地执行、模型转发、供应商 token 适配、运行时拦截”。

### 1.3 建设价值
企业部署 AI Agent 后，技能包、客户端版本、用户身份与设备关系往往分散在 IM、网盘和人工流程中，导致发现成本高、版本不一致、排障困难、缺乏可视化管理，也难以与统一账号体系打通。woicrew中央控管系统通过技能中心、版本中心、设备绑定和统一认证来解决这些问题。

## 2. 产品目标
### 2.1 总体目标
建设一套可产品化、可部署、可复刻的企业级 AI Agent 中央控管系统，支撑企业统一进行：

+ 客户端版本管理与下载分发；
+ 技能包上传、审核、展示、下载；
+ Web 与客户端双轨认证；
+ 设备与用户关系维护；
+ 模型清单集中配置；
+ 管理后台运营治理。

### 2.2 具体目标
1. **统一入口**：版本、技能、文档均有统一访问入口。
2. **统一身份**：通过企业 IAM 完成登录，Web 侧走 Session，客户端走 JWT。
3. **统一治理**：管理员可在管理台审核技能、维护版本、查询设备。
4. **统一对接**：客户端通过标准 API 完成登录、上报、查询、上传与下载。
5. **统一扩展基础**：为后续加入审计、授权、灰度、扫描、设备控制预留能力。

### 2.3 成功标准
+ 技能使用者可检索、查看、下载已通过审核的技能；
+ 技能贡献者可上传符合规范的技能包；
+ 平台管理员可审核技能、维护客户端版本、按条件检索设备记录；
+ 客户端可完成登录拿 JWT、设备上报、模型列表获取、技能上传与技能下载；
+ 系统支持二级路径部署与标准反向代理接入。

## 5. 产品交付形态
### 5.1 营销/门户首页
面向所有用户提供品牌与能力展示，承担产品入口与 CTA 引导作用，支持导向下载中心和文档。

### 5.2 工具型 Web 应用
在统一公共布局下，提供技能浏览、搜索、详情、下载、上传，以及独立下载中心和 Markdown 文档站。普通页面由统一 Layout 承载。

### 5.3 管理后台
采用左侧导航 + 右侧内容区布局，仅对已登录且 `isAdmin=true` 的用户开放；未授权访问应重定向到首页或被拦截。

### 5.4 开放 API
供桌面客户端调用的 JSON / 文件接口，与浏览器页面并行存在，覆盖登录、设备、模型、技能上传与技能下载等场景。

## 9. 核心业务流程
### 9.1 Web 登录流程
1. 用户访问需要登录的页面；
2. 前端调用当前用户信息接口判断是否已登录；
3. 未登录时跳转企业 IAM；
4. IAM 完成认证后回调系统；
5. 系统创建 Session；
6. 前端刷新用户信息；
7. 若 `isAdmin=true`，显示后台访问能力。

### 9.2 客户端登录取 JWT 流程
1. 客户端请求登录入口，如 `/auth/login?client=woiclaw`；
2. 用户在企业 IAM 完成认证；
3. 系统完成回调；
4. 系统签发应用侧 JWT；
5. 通过约定 redirect 方式返回给客户端；
6. 客户端后续以 Bearer Token 调用 API。

### 9.3 技能上传流程
1. 上传者登录；
2. 选择技能 ZIP；
3. 前端解析 `SKILL.md` 与 frontmatter；
4. 校验关键字段；
5. 调用上传接口；
6. 后端落库并保存 ZIP；
7. 平台管理员进入后台审核。

### 9.4 技能下载流程
1. 用户在列表或详情页点击下载；
2. 系统按 slug 返回 ZIP；
3. 成功下载后增加 `download_count`；
4. 客户端或浏览器保存文件。

### 9.5 设备上报流程
1. 客户端带 JWT 调用设备上报接口；
2. 提交 device_uuid、OS、应用版本等信息；
3. 系统从 JWT 或上下文识别用户；
4. 按 device_uuid 幂等写入或更新设备记录；
5. 形成设备与用户绑定关系。

## 10. 功能需求明细
### 10.1 应用管理
#### 10.1.1 发布版本维护
系统应允许管理员维护发布版本，包括：

+ version
+ date
+ 中文标题
+ 英文标题
+ 中文更新说明
+ 英文更新说明
+ Windows 下载 URL
+ Mac Intel 下载 URL
+ Mac ARM 下载 URL

#### 10.1.2 下载中心展示
系统应向普通用户展示：

+ 当前可下载版本；
+ 历史版本；
+ 各平台链接；
+ 中英文更新说明。

#### 10.1.3 发布记录删除与编辑
管理员应可删除发布版本，并支持行内更新下载 URL。

---

### 10.2 认证中心
#### 10.2.1 企业 IAM 对接
系统必须接入企业统一身份平台，作为 Web 与客户端的统一认证入口。

#### 10.2.2 双轨认证策略
+ **Web 侧**：基于服务端 Session；
+ **客户端侧**：基于 Bearer JWT。

#### 10.2.3 当前用户接口
应返回：

+ 账号 account
+ 用户名 name
+ 用户标识 user_id
+ 是否管理员 isAdmin

#### 10.2.4 登出
系统应提供清理 Session 并跳转登出或统一退出逻辑的能力。

#### 10.2.5 安全要求
+ redirect_uri 必须做白名单控制；
+ Cookie 名称与 Path 应可配置，且与基路径联动，避免同域冲突；
+ `SESSION_SECRET` 与 `JWT_SECRET` 需独立配置。

---

### 10.3 技能仓库
#### 10.3.1 技能列表
系统前台只展示 `status = 已通过` 的技能。

#### 10.3.2 技能搜索
应支持按名称、描述、发布者等进行模糊搜索。

#### 10.3.3 技能详情
详情页至少应展示：

+ slug
+ name
+ description
+ version
+ publisher
+ category
+ status
+ download_count
+ uploader_account
+ 时间戳

#### 10.3.4 技能上传
系统支持两种上传方式：

+ Web Session 上传；
+ 客户端 Bearer Token 上传。

#### 10.3.5 技能元数据规范
技能包通常为 ZIP，内部包含 `SKILL.md` 及脚本/资源。`SKILL.md` 需提供 YAML frontmatter，前端/后端至少校验以下字段：

+ slug
+ name
+ version
+ publisher
+ description

且本期强制 `version`、`publisher` 非空。

#### 10.3.6 技能状态流转
本期最少需要支持：

+ 待审核
+ 已通过
+ 已驳回

管理员可在后台执行通过或驳回。

#### 10.3.7 技能删除
管理员可删除技能；如需支持上传者删除本人技能，应在详细设计中明确授权规则。

---

### 10.4 设备管理
#### 10.4.1 设备上报
设备记录至少包含：

+ device_uuid
+ account
+ user_id
+ user_name
+ phone
+ token
+ os_name / os_version
+ app_version
+ created_at / updated_at

#### 10.4.2 设备幂等
设备上报必须以 `device_uuid` 为幂等键，重复上报更新原记录。

#### 10.4.3 按设备查用户
系统需支持通过设备 ID 查询绑定用户；若该记录存有 token，则需在 token 有效时才返回用户信息，否则返回 401。

#### 10.4.4 管理台设备查询
管理员应可：

+ 按账号搜索；
+ 按用户名称搜索；
+ 按设备 UUID 搜索；
+ 分页查看结果；
+ 复制 UUID。

---

### 10.5 模型配置
#### 10.5.1 模型清单
系统应维护模型表，并通过公共接口返回模型列表。

#### 10.5.2 模型字段
至少包括：

+ key
+ value
+ image

#### 10.5.3 模型边界
本系统只负责“可选模型清单”的配置与下发，不负责真实的模型网关权限校验或调用转发。复刻时必须确保模型 key 与真实 LLM 网关对齐，避免“界面可选、实际无权限调用”。

### 10.6 管理后台

#### 10.6.2 管理功能范围
后台至少包括：

+ 安装包管理；
+ 安装包导入；
+ 技能审核管理；

## 12. 接口需求
### 12.1 设计原则
+ REST 风格优先；
+ 页面接口与客户端接口可以共享资源但认证方式不同；
+ 统一错误码与错误消息；
+ 文件接口应支持浏览器与客户端双场景；
+ 支持基路径前缀部署。

### 12.2 核心接口分组
#### 认证相关
+ `GET /auth/login`
+ `GET /auth/callback`
+ `GET /auth/userinfo`
+ `GET /auth/logout`

#### 技能相关
+ `GET /api/skills`
+ `GET /api/skills/search`
+ `GET /api/skills/{slug}`
+ `GET /api/skills/download`
+ `POST /api/upload`
+ `POST /api/skills-upload`

#### 设备相关
+ `POST /api/device-report`
+ `GET /api/user-by-device`
+ `GET /api/get-user`

#### 模型相关
+ `GET /api/models`

#### 管理后台相关
+ 发布版本管理接口
+ 技能审核与删除接口
+ 设备分页检索接口

## 13. 数据与存储设计
### 13.1 逻辑实体
| 实体 | 主要字段 | 存储位置 |
| --- | --- | --- |
| Skill | slug, name, description, version, publisher, category, status, download_count, uploader_account, 时间戳 | 表 `skills`；ZIP 文件存 `bundles/` |
| DeviceReport | device_uuid, account, user_id, user_name, phone, token, os_*, app_version, created_at, updated_at | 表 `device_reports` |
| ReleaseVersion | version, date, 中英标题/内容, 各平台 URL | 表 `release_versions` |
| Model | key, value, image 等 | 表 `models` |
| Admin | account | 表 `admins` |


### 13.2 数据库与文件系统要求
+ 开发默认可用 SQLite；
+ 生产建议支持 MySQL；
+ 使用异步 SQLAlchemy；
+ 技能 ZIP 与发布包应通过 `DATA_DIR`、`BUNDLES_DIR`、`RELEASES_DIR` 等路径配置落盘。

### 13.3 关键业务规则
+ 前台只显示已通过技能；
+ 下载成功增加 `download_count`；
+ 设备上报按 `device_uuid` 幂等更新；
+ `user-by-device` 需遵循 token 有效性校验。

## 15. 非功能需求
### 15.1 性能
+ 列表接口必须分页；
+ 内网场景建议列表接口 P95 小于 500ms，但最终需以实际数据量压测为准；
+ 大文件上传需结合反向代理大小和超时进行配置。

### 15.2 安全
+ 生产强制 HTTPS；
+ `SESSION_SECRET` 必须高强度随机；
+ `SESSION_COOKIE_NAME` 与 Path 必须可配置，并与 `WOICREW_BASE_PATH` 联动，避免同域冲突；
+ `JWT_SECRET` 独立管理；
+ 技能 ZIP 必须做格式校验；
+ 第三方复刻时必须明确是否存 token，以及按设备取用户的安全模型。

### 15.3 可部署性
+ 前端应支持 `basename` 子路径挂载；
+ 后端支持反向代理部署；
+ 系统适配 Docker / Nginx；
+ 配置项通过环境变量管理。

### 15.4 可扩展性
+ 文件存储后续可替换为对象存储；
+ 管理员来源可扩展为 IAM 角色映射；
+ 模型配置可扩展排序、分组、启停；
+ 设备管理可扩展远程操作与更多台账字段。

## 16. 部署与集成要求
### 16.1 推荐部署形态
+ 前端：React 18 + Vite 6 构建产物；
+ 后端：API 服务；
+ 数据库：SQLite / MySQL；
+ 反向代理：Nginx；
+ 认证：企业 IAM；
+ 存储：本地目录，后续可替换对象存储。

### 16.2 子路径部署
系统需支持挂载于二级路径，例如 `/woicrew`。前端路由 `basename`、后端路径前缀、Cookie Path 与 Nginx 转发规则必须一致。

### 16.3 与外部系统集成
+ 企业 IAM / IdP；
+ 客户端壳程序；
+ LLM Proxy；
+ 文件存储或制品仓库；
+ 企业 DNS、证书与反向代理体系。

## 17. 验收标准
### 17.1 功能验收
+ 登录成功后 Web 可建立 Session；
+ 客户端可成功获取 JWT；
+ 技能上传时会校验 `SKILL.md` 与关键 frontmatter；
+ 已通过技能可在前台展示和下载；
+ 下载成功后计数增加；
+ 管理员可在后台通过/驳回/删除技能；
+ 管理员可维护版本与下载 URL；
+ 客户端可设备上报并被后台检索；
+ `user-by-device` 能按既定安全规则返回用户；
+ `/api/models` 可返回模型清单。

### 17.2 非功能验收
+ 支持二级路径部署；
+ 支持 Docker + Nginx；
+ Cookie Path、基路径、路由前缀一致；
+ 列表与后台接口支持分页；
+ HTTPS 环境运行正常。
